A demo you can run · one day · six scenes · no model in any of them

One hard question,
three agents.

dear‑guide keeps a project's decisions and the work that follows from them in two linked stores. These six scenes are one day on a project: a question too big for one pass, three agents let loose on it, and the concurrency problems that day runs into — in the order it runs into them.

Every line of terminal output on these slides is verbatim from running the scripts. Four of the six end with the tool doing something about it. One does not, and it is the reason the other five are worth having.

$ ./demo-agentic/demo.sh
$ ./demo-agentic/demo.sh 4   # just the one that matters

→ to advance a step, ← to go back.

The setup

An open-source Go engine, three decisions deep

One premise and a question hanging off it in each of two areas — plus a third agent on the premise itself, which is what makes the other two wait. The smallest shape in which separate work still collides.

D01 DECIDED agent A
Where do the evaluation weights come from?
“Hand-tuned, by us. Three strong players on the team and no GPU budget, so the cheap thing is also the only thing.”
falsifier  a GPU budget appears, or hand-tuning stalls for two releases running
D02 OPEN agent B
How is a weight change accepted?
D03 OPEN agent C
What ships in the release binary?
T01  Wire the SPRT harness to the volunteer cluster   DOING  · evidence for D02
T02  Measure the binary with the weights inlined   DONE  · evidence for D03  → 412 KB at -Os, weights 71 KB of it

Every vertex here is a question the team answers in a design discussion — where the weights are sourced, how a change gets reviewed, what the release artefact is. None of it is anything the engine does while playing. This graph guides the development of a system; it is not a model of one.

Three questions, and an order between them — not a rule anybody wrote down, but the edges, recorded when each question was opened.

This is more than one pass can hold and each question belongs to a different area, so three agents are launched onto it: A on the premise, B on Tooling, C on Release.

Two of the three are about to work on a premise nobody has settled. That is what parallel exploration is — and the graph already knows it.

Scene 2 · three agents, one staging tray

Who staged what, and who may apply it

The agents were launched where the problem is: the maintainer's checkout. A directory is one staging tray. Played twice, with the same commands both times.

agent C · Release

$ dg decide D02 --answer 'SPRT against the previous build…'
staged 1 op(s)

So does B.

$ dg apply (nobody named)

One was C's. Two were half-finished answers belonging to agents still working on them.

$ dg pending
nothing staged

A's only signal — which reads as my staging failed, and invites A to write it again.

$ export DG_AGENT=A  # and B, and C — set by whoever launches them
STAGED  3 op(s)
  0  gqrv  close  D01  A trained net, 40 MB…                      ·  by A
  1  syum  close  D02  SPRT against the previous build…           ·  by B
  2  hbnp  close  D03  One binary, no runtime files…              ·  by C

Same tray, same three answers — and now each says whose it is.

$ dg apply (as A)
✓ applied 1 op(s) → decisions.json + decision-graph.md
2 op(s) left staged, by B, C

A's own op written; A is told exactly what it left and whose.

One variable, and a shared tray stops being a place where one agent can publish another's draft. A close is the op this tool deliberately makes hard to take back — the way out is dg reopen, which files a reversal that never happened.

Nothing here is isolated. The three still share one graph and can still see each other's work, and that is the point rather than the problem.

Scene 3 · three answers at once

Composition parallelises; publication is ordered

All three compose at the same time and nothing stops them. What is ordered is the moment each answer becomes part of the record.

agent A · Core
agent C · Release
agent B · Tooling
$ dg pending
STAGED  3 op(s)   — three answers, three authors, none of it written
$ dg apply --mine
✗ aborted, nothing written
[propagation] D02 is DECIDED but rests on D01 (REOPENED) — `dg repair` marks it PROVISIONAL, or settle the premise with `dg decide D01`

B did nothing wrong. B was asked to answer D02. Nothing was written and B's answer is still B's.

$ dg apply --mine
✓ applied 1 op(s)

The premise goes first.

$ dg apply --mine (the same op, unchanged)
✓ applied 1 op(s)

Nothing was re-composed. It simply became legal.

Nobody sequenced the agents, nobody held a lock, and nobody had to know what the others were doing. Three agents ran flat out, one was told not yet in a sentence naming the premise and both exits, and the graph never held a state anybody would have to unpick.

The order was the edge — recorded months earlier, when the question was opened.

One line. Printed once. To a process that may not have been reading.

$ dg check  ·  $ dg why D03
✓ 3 vertices, 4 edges; 2 tasks, all invariants hold, 1 warning(s)

D03  "the weights compile in as a generated header"
D01  "A trained net, 40 MB"
→ every premise under this is settled

The one warning is about T01 and has nothing to do with the contradiction. The honesty machinery is working and pointed elsewhere.

dg check is not wrong. The structure is valid; the two answers contradict each other in the prose, where no invariant can reach. This graph is as clean as the tool can certify and it describes a release that cannot be built.

Scene 2's failure was attribution and closed with a name. Scene 3's was ordering and closed with an edge. This is neither — every op was owned and every premise was settled before it was built on. A clone of its own would have made it more likely, not less.

What saves it is the falsifier C wrote before it had any reason to — “the weights outgrow what a header can carry”. They now have, so the exit is a command rather than an argument.

An agent that cannot tell 5a from 5b puts two vertices behind one question, which is the disorder the unique-id rule exists to prevent. The tool cannot make that call and does not pretend to.

What dg range --set 50-99 does is make the collision rare — so the integration report a person reads is not a rename line per record anybody wrote, which is the volume that trains a reader to stop reading it.

Scene 6 · bringing the parallel work back

What git cannot merge, and the seam

Isolation did not remove the race. It moved it.

6a · two additions
git
6b · two answers
$ git pull
CONFLICT (content): Merge conflict in decisions.json

Two unrelated questions, different ids, valid batches, clean applies — and a JSON array merges as text.

$ dg render  ·  $ dg check
✓ all invariants hold

A union handles two additions. This step is what makes it safe rather than merely merged.

$ dg decide D50 (B, after pulling A's answer)
D50 already has an answer, and is DECIDED — `dg reopen` it first

Refused before anything is staged, let alone merged.

a unionwould pick one
silently

A text merge would put both edges in the file and dg check would refuse the result. A union keyed by id would pick one silently, which is worse than either.

Two answers to one question is not a merge problem to be resolved. It is a disagreement between two agents, and only a person who knows which is right can settle it — which is what dg integrate and dg incoming --take/--keep/--split are for: every conflict collected first, then one person answers a list once.

What this is, and what it is not

Now run it yourself

What it shows

What dg does when several writers meet: which contradictions it refuses, which it merely reports, and which are left to you. One day, six scenes, reproducible to the line.

What it does not

There is no model in this demo. The agents are shell scripts, because a race has to be deterministic to be a demo and this has to run offline in CI. Whether an agent reads the drift line in scene 4 and acts on it is the question these scenes cannot answer.

The claim, and it is narrow

Several agents on one graph is a configuration this tool copes with, not one it guarantees. Attribution is closed, ordering is closed, collisions are refused and made rare, two answers to one question go to a person. Scene 4 is not closed, and no locking discipline closes it — which is why the falsifier does the most work under a fan-out.

One scene is missing

The commit gate under a fan-out. On opencode the gate does not see subagent shell calls, so a commit from inside a spawned agent is ungated — the sharpest agent-specific failure this project knows about. Showing it needs a real subagent, which breaks the rule the rest is built on. It is named rather than faked.
