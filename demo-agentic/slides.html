A demo you can run · five scenes · no model in any of them

Two agents,
one graph.

dear‑guide keeps a project's decisions and the work that follows from them in two linked stores. It was built for one writer. These five scenes are what happens when there are two — a pair of AI agents given separate work on the same graph, racing.

Every line of terminal output on these slides is verbatim from running the scripts. Nothing here is illustrative, and the interesting result is not that the store breaks. It doesn't.

$ ./demo-agentic/demo.sh
$ ./demo-agentic/demo.sh 3   # just the one that matters

→ to advance a step, ← to go back.

The setup

An open-source chess engine, three decisions deep

One premise, with a question hanging off it in each of two agents' areas. That is the smallest shape in which two agents can be given genuinely separate work and still collide.

D01 DECIDED
Where do the evaluation weights come from?
“Hand-tuned, by us. Three strong players on the team and no GPU budget, so the cheap thing is also the only thing.”
falsifier  a GPU budget appears, or hand-tuning stalls for two releases running
D02 OPEN agent A
How is a weight change accepted?
D03 OPEN agent B
What ships in the release binary?
T01  Wire the SPRT harness to the volunteer cluster   DOING  · evidence for D02
T02  Measure the binary with the weights inlined   DONE  · evidence for D03  → 412 KB at -Os, weights 71 KB of it

Every vertex here is a question the team answers in a design discussion — where the weights are sourced, how a change gets reviewed, what the release artefact is. None of it is anything the engine does while playing. This graph guides the development of a system; it is not a model of one.

Scene 1 · one project, two agents in it

The tray has no idea whose ops are whose

They share a directory, so they share a staging tray. Nothing either of them types is wrong.

and become PROVISIONAL:
  D02

D02 is OPEN in the store. It is decided only in the tray, by A, and unapplied. B has just been told about work that is not B's and that B has never seen.

tray3 ops
2 authors
$ dg pending
STAGED  3 op(s)
  0 close      D02 ← A's
  1 reopen     D01 ← B's
  2 set_status D02 ← B's,
                     about A's

Nothing in the tray records which is which.

$ dg apply
✓ applied 3 op(s) → decisions.json
                 + decision-graph.md

B applied A's decision.

$ dg pending
nothing staged

A's only signal. Not that the work landed; not that the ground moved under it.

$ dg decide D02 … (again — surely it failed?)
D02 already has an answer, and is PROVISIONAL — `dg confirm` it if it still holds, or `dg reopen` it

And here the tool catches it, accurately, naming both exits.

The resulting graph is correct. D02 is PROVISIONAL, the propagation is right, dg check is clean, nothing is corrupt. What went wrong is that A's answer was published at a moment A did not choose, by a process that did not know it was publishing it.

The store never breaks. What breaks is an agent's model of it — and the agent finds out only by trying to write.

Scene 2 · the same setup, played the supported way

What one writer at a time actually costs

agent A
one tray
agent B
$ dg decide D02 …
staged 1 op(s)
$ dg pending — before staging anything
STAGED  1 op(s)
  0 close D02 SPRT against the…

… and stops, because that op is not B's.

That is the whole protocol. dg pending costs nothing, needs no flag, and turns scene 1 into a non-event.

It is also a habit — and nothing observable reveals that an agent skipped the look. Two people in two terminals keep it, because they are one intent with two hands. Two agents are two intents.

→ every premise under this is settled

Four lines apart, in one command's output: the weights compile in as a generated header, and a trained net, 40 MB. Underneath them, every premise under this is settled.

This graph is as clean as the tool can certify, and it describes a release process that cannot produce a release. dg check is not wrong — the structure is valid. The contradiction is in the prose, where no invariant can reach.

The only thing in the entire system that said so was that one drift line, printed once, at apply time, to a process that may not have been reading.

How it ends. A's falsifier has fired, so the exit is a command rather than a judgement call:

$ dg reopen D03 --why "its falsifier fired: D01 moved to a 40 MB net" --yes

Drift does not prevent the stale answer. It is the one chance anybody gets to notice — and everything after it depends on the falsifier having been written first.

Scene 4 · three interleavings, three refusals

The loud one, and the two collisions

Worded three different ways on purpose. An agent that cannot tell the last two apart puts two vertices behind one question.

4a — B only reopens D01. A's close would put a DECIDED vertex on a REOPENED premise.
✗ aborted, nothing written
would leave the graph invalid:
  [propagation] D02 is DECIDED but rests on D01 (REOPENED) — `dg repair` marks it PROVISIONAL, or settle the premise with `dg decide D01`
4b — both agents reach for the next free id, for different questions.
✗ aborted, nothing written
D04 already exists, and is not what this op would have created — pick another id
4c — both notice the same gap and file it identically. The commoner case.
· refused — another writer got there first
D05 already has this vertex, identical to the op staged — another writer applied it while this batch was waiting. Nothing of yours was lost; it is in the store, and the tray holds a duplicate of it.

4a read beside scene 3 is the boundary. The same race, one notch further, and the tool goes from a one-line note to a refusal. What separates them is whether the resulting structure is legal — and that does not track how wrong the answer is. “A human can explain every weight” under a 40 MB net is refused; “412 KB, compiled into the binary” under the same net lands clean.

4c is why the message spends four lines saying nothing of yours was lost. An agent that reads it as my work failed re-files under a fresh id, and the graph ends up with one question behind two vertices — a fault nothing downstream can detect, because both are individually valid.

Unrelated questions. Different ids. Valid batches. Clean applies on both sides. And the graph will not merge.

$ git checkout --ours decision-graph.md
$ python3 ../union.py # the two vertex lists
$ dg render && dg check
✓ 5 vertices, 1 edges; 2 tasks,
  all invariants hold, 1 warning(s)

Both agents' questions survived the union. The one warning is the standing evidence_unharvested on D03 — this scene never settled it — not anything about the merge.

decisions.json is a JSON array and git merges it as text. This is what the isolation cost: scenes 1 and 2 cannot happen once each agent has its own clone, and this can — in git, where dg has no visibility at all.

Two facts make the resolution safe. decision-graph.md is generated, so it is never resolved by hand. And dg check is the merge test: a vertex dropped or an edge target lost is a structural fault, which is exactly the kind this tool catches.

So scene 5 ends somewhere scene 3 does not. There, the graph was clean and wrong and one line ever said so. Here, the damage a bad resolution can do is the damage dg check is built to find.

What this is, and what it is not

Now run it yourself

What it shows

What dg does when two writers meet: which contradictions it refuses, which it merely reports, and which are left to you. Five interleavings, reproducible to the line.

What it does not

There is no model in this demo. The agents are shell scripts, because a race has to be deterministic to be a demo and this has to run offline in CI. Whether an agent reads the drift line in scene 3 and acts on it is the question these scenes cannot answer.

And it is not a retraction

None of it makes two agents supported. The answer stays one writer at a time — these scenes are the evidence for that sentence, not an argument against it.

One scene is missing

The commit gate under two agents. On opencode the gate does not see subagent shell calls, so a commit from inside a spawned agent is ungated — the sharpest agent-specific failure this project knows about. Showing it needs a real subagent, which breaks the rule the rest is built on. It is named rather than faked.
