A demo you can run · one day · seven scenes · no model in any of them

Three agents,
one graph,
a day's work.

dear‑guide keeps a project's decisions and the work that follows from them in two linked stores. Here three software agents are put on one graph, and the work is what drives everything: the task graph says what is ready, an agent picks it up, doing it produces evidence, and evidence is what settles a question.

Nobody in this demo invents an answer. The concurrency problems arrive the way they actually do — out of three agents doing real work and then having to join it up. Every line of terminal output is verbatim from running the scripts.

$ ./demo-agentic/demo.sh
$ ./demo-agentic/demo.sh 7   # the two nothing prevents

→ to advance a step, ← to go back.

The setup

An open-source Go engine, three decisions deep

One premise, a question in each of two areas, and the work outstanding against them. The work is the half that makes this a day rather than a diagram.

D01 DECIDED
Where do the evaluation weights come from?
“Hand-tuned, by us. Three strong players on the team and no GPU budget, so the cheap thing is also the only thing.”
falsifier  a GPU budget appears, or hand-tuning stalls for two releases running
D02 OPEN
How is a weight change accepted?
T01  will produce the evidence  · not started
D03 OPEN
What ships in the release binary?
T02  already reported  · nobody wrote down what it meant
T01  Wire the SPRT harness to the volunteer cluster   TODO  · evidence for D02  · nothing blocks it
T02  Measure the binary with the weights inlined   DONE  · evidence for D03  → 412 KB at -Os, weights 71 KB of it
T03  Draft the release note   TODO  · because D03 — blocked by a question, not by work

Three different kinds of outstanding thing, and a person wrote none of them down as a plan. An answer is owed, a task is ready, and a task is blocked by an unanswered question. That is scene 1.

Scene 1 · nobody writes the plan

The queue is the assignment

The maintainer is about to put three agents on this. They do not ask for work; they ask the graph.

→
what comes back
$ dg check
! [evidence_unharvested] T02 is DONE and was to inform D03, which is still unsettled — record what it showed with `dg decide D03`

An answer is owed. T02 measured the binary in March; nobody ever wrote down what the number meant.

$ dg task
TASKS  2 outstanding of 3
  T01 TODO  evidence for D02
  T03 TODO  waits D03 (undecided)
ready T01

A task is ready — computed from the edges, stored nowhere. And a task is blocked by a question, not by other work.

Agent A takes the answer that is owed. Agent B takes the ready task. Agent C has nothing yet — which is a real state, and where scene 2 starts.

Scene 2 · the work opens up

Decomposition is what makes the parallelism

B picks up T01 and does what an agent actually does first: finds out what is in it.

agent B · Tooling
the queue
what changed
$ dg task add T04  ·  dg task add T05 --after T04
$ dg task dep T01 --after T04,T05
✓ applied 6 op(s) → tasks.json

Wiring a harness to somebody else's cluster is three things, and two of them are somebody else's to give.

$ dg task
T01 DOING  waits T04, T05
T04 TODO   unblocks T01, T05
T05 TODO   waits T04
ready T04

A moment ago there was one ready task and three agents.

B looked at its own work, and in doing so produced startable work for somebody else. Nobody scheduled that. The agent that picks T04 up has not been told about it — it will find it the way B found T01.

Everything that goes wrong from here goes wrong because of that, and not because a script arranged it.

Scene 3 · no status is updated

and the work still joins up

Agent C, which had nothing to do in scene 1, takes the task B's decomposition freed.

agent C writes one thing
→
and two others move
$ dg task done T04 --outcome 'sponsor issued a service account…'
✓ applied 1 op(s)

C did not update T05, did not notify B, and does not know B exists.

$ dg task
T01 DOING  waits T05   (was: waits T04, T05)
T05 TODO   unblocks T01
ready T05       (was: waits T04)

Blocked is derived, never stored. No status could have gone stale; no message could have been missed.

Two agents just handed work to each other through the graph, and the handover cost one command by one of them. This is the part that makes a fan-out survivable at all.

ready T03, T05

T03 was not ready a moment ago. It was waits D03 (undecided).

$ dg task done T01  ·  $ dg check
! [evidence_unharvested] T01 is DONE and was to inform D02, which is still unsettled

The graph asks B for the answer the work just earned.

$ dg decide D02 --source 'T01: harness live, verdict in the CI log'
✓ 3 vertices, 3 edges; 5 tasks, all invariants hold

Two questions settled, and neither answer was invented — each cites the task whose outcome produced it. Three tasks finished by two agents who never spoke. One question being answered turned a blocked task into a ready one.

That is the loop this tool exists for. Everything from here is what happens when it is running and something moves underneath it.

Scene 5 · three agents, one staging tray

Whose op is whose

The agents were launched where the work is. A directory is one staging tray, so everything scenes 2 to 4 composed went through the same file.

agent A · Core
agent C · Release
agent B · Tooling
# nobody named — the way a harness gets it by forgetting
A: dg decide D03   staged, still checking it
B: dg task done T05   staged, not yet verified
C: dg task add T06  a chore C noticed
$ dg apply
✓ applied 1 op(s) → decisions.json
✓ applied 3 op(s) → tasks.json

C wrote its own op and both of the others — an answer A had not finished checking, a completion B had not verified.

$ dg pending
nothing staged

Which reads as my staging failed, and invites A to write the answer a second time.

$ export DG_AGENT=A  # and B, and C. Same commands, same order.
STAGED  1 op(s)
  0  rfbj  close  D03  One binary, no runtime files…   ·  by A
STAGED TASKS  1 op(s)
  0  ngfq  set_status  T05  → DONE                    ·  by B
$ dg apply (as C)
✓ applied 2 op(s) → tasks.json
2 op(s) left staged, by A, B

C's own chore written; A's answer is still A's to finish.

A close is the op this tool deliberately makes hardest to take back — the way out is dg reopen, which files a reversal that never happened.

Nothing here is isolated. All three still share one graph and still hand tasks to each other the way scene 3 showed. What changed is only that publishing is now something an agent does to its own work.

The day's work is done. Two questions settled on evidence two agents produced, three tasks finished, one blocked task released. Then the maintainer gets a mail.

The falsifier, written 2026-03-01, said: a GPU budget appears. Nobody has to argue.

$ dg show
FRONTIER  PROVISIONAL 2  REOPENED 1
  D02 PROVISIONAL  · D01
  D03 PROVISIONAL  · D01

Three agents worked in parallel on a premise, and one fact put all of it under review at once.

The maintainer did not work that set out. dg reopen computed it and dg check refuses a store where it was not applied. What a fan-out costs, stated exactly — and what the graph gives you is the list.

Nothing is lost. Both answers are still there, still cite the tasks that produced them, and dg confirm is what says re-read under the new premise and it still holds.

Scene 7 · the two nothing prevents  ·  the one to read

A quiet agent, and a stale answer

7a · an agent stops
·
7b · the world moves
$ dg task park T01 --why 'cluster queue is six days deep…'
! [evidence_stalled] D02 is OPEN and waits on evidence nobody is producing — T01 is parked and no other task meant to inform it is still going

Not about B at all. A question with no route to an answer — visible only at the seam: the task store knows T01 stopped, the decision store knows D02 is open, and only the link says those are one problem.

$ dg apply --mine (A, returning to a staged answer)
· D01 moved since this batch was staged (its answer changed) — op 0 (close D03) rests on it
✓ applied 1 op(s)

Its answer changed. Not the status, not the structure. The premise still says what kind of thing it is; it now says something else about it.

$ dg check  ·  $ dg why D03
✓ 3 vertices, 3 edges; 5 tasks, all invariants hold

D03  "the weights compile in as a generated header"
D01  "A trained net, 40 MB"
→ every premise under this is settled

Four lines apart, in one command's output.

dg check is not wrong. The structure is valid; the two answers contradict each other in the prose, where no invariant can reach.

Scene 5 was attribution and closed with a name. Scene 3 was coordination and closed because readiness is derived. Scene 6 was propagation and closed because reopen computes the set. This is none of those — A owned its op, cited real evidence, and the world moved while the answer sat in a tray. Giving A a clone of its own would have made it more likely, not less.

What saves it is the falsifier A wrote before it had any reason to — “the weights outgrow what a header can carry”. They now have, so the exit is a command rather than an argument.

What this is, and what it is not

Now run it yourself

What it shows

What dg does when several agents work one graph: how the work is handed out, how it joins back up, and which contradictions are refused, reported, or left to you. One day, seven scenes, reproducible to the line.

What it does not

There is no model in this demo. The agents are shell scripts, because a race has to be deterministic to be a demo and this has to run offline in CI. Whether an agent reads the drift line in scene 7 and acts on it is the question these scenes cannot answer.

The claim, and it is narrow

Several agents on one graph is a configuration this tool copes with, not one it guarantees. Attribution is closed, ordering is closed, collisions are refused and made rare, two answers to one question go to a person. Scene 7 is not closed, and no locking discipline closes it — which is why the falsifier does the most work under a fan-out.

One scene is missing

The commit gate under a fan-out. On opencode the gate does not see subagent shell calls, so a commit from inside a spawned agent is ungated — the sharpest agent-specific failure this project knows about. Showing it needs a real subagent, which breaks the rule the rest is built on. It is named rather than faked.
