Routing long edges around the boxes they used to cross
======================================================

The web view lays the graph out with the classic layered (Sugiyama) method,
in `dgraph/static/app.html`: rank by longest path from a root, order within
each rank by barycentre, four sweeps. About forty lines, no dependency.

What it did not do was break a multi-rank edge into per-rank waypoints. So
an edge spanning three ranks was drawn as one straight line, and that line
went through whatever boxes lay between.

    store        nodes   edges   spanning >1 rank   drawn THROUGH a box
    n200d6         200   1,144      505 (44%)        500  (99% of those)
    n1000d6      1,000   5,720    2,676 (47%)      2,633  (98% of those)
    n2000d6      2,000  11,440    5,441 (48%)      5,358  (99% of those)

Essentially every long edge crossed a node, and about 46% of all edges did.


--- Two things that did not work, recorded so they are not retried ---------

**Crossing count is the wrong metric.** Adding waypoints makes the classic
edge-crossing count slightly *worse* (about 6%), not better. A straight line
between two well-placed endpoints already routes well; what it cannot do is
get out of the way. Judge this by box overlap, not by crossings.

**More barycentre sweeps buy nothing.** Measured at 4, 8, 16, 24, 32 and 48
sweeps, the crossing count is *identical* — the sort reaches a fixed point
almost immediately. The four in the code are not a tuning choice to revisit.

**A waypoint must not take a node's width.** The obvious implementation gives
each placeholder a full `NW+GAPX` slot, and it works — 19% to 61% fewer
overlaps — but the canvas goes 4.2x wider (21,948 -> 92,564 px at 2,000
nodes), which costs far more readability than the routing wins back. A
waypoint is a bend in a line, not a box: an 18 px lane is enough.


--- What shipped ----------------------------------------------------------

Waypoints at 18 px lanes. Measured against the same layout without them:

    store        nodes   through a box      canvas         layout
    real40          40     47 ->  31  -34%   608 ->   644    2 -> 5 ms
    real80          80     90 ->  81  -10%   996 -> 1,086    1 -> 3 ms
    real150        150    168 -> 139  -17% 1,966 -> 1,966    1 -> 5 ms
    n1000d6      1,000  2,643 -> 2,581 -2% 10,308 -> 13,422 20 -> 62 ms

**The metric understates it.** It counts a line clipping a box corner the
same as a line running down through the middle of a title, and it is the
second kind that is gone. Rendered before and after at 40 nodes, the change
is unambiguous: the long edges used to run vertically through the centre of
five or six boxes in a column, over the text; they now sweep around the
margins and pass between boxes.

At 1,000+ nodes the gain is ~2%, because a rank of a hundred 168 px boxes
with 26 px gaps has nowhere to route anything. That is a saturated layout and
no amount of waypoint placement fixes it — the answer there is to show less
of the graph at once, which is a question about the page rather than about
the algorithm.

Reproduce with `node benchmarks/layout_ab.js <store>...` against the stores
`gen_store.py` writes.
