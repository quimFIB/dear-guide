The three local fixes, measured at 2,500 and 10,000 vertices
============================================================

Run 2026-08-29 by `probe_easy.py`, on stores regenerated from
`gen_store.py` (deterministic; seed 7 / 11, byte-identical to the ones the
main sweep used, so these numbers sit alongside `raw.json` directly).

    python3 benchmarks/gen_store.py /tmp/dg-bench/n2500d6  --vertices 2500  --degree 6
    python3 benchmarks/gen_store.py /tmp/dg-bench/n10000d6 --vertices 10000 --degree 6

Every variant asserts it returns the identical answer before it is timed;
all assertions passed at both sizes.


--- 2,500 vertices, reps=2 -------------------------------------------------

$ python3 benchmarks/probe_easy.py --store /tmp/dg-bench/n2500d6 --reps 2

store: 2,500 vertices, 2,767 edge records

fix                              now (ms)   after (ms)   speedup
A  find prose (lens cache)        2,735.6        484.3      5.6x
B  stale_provisional             14,590.3          3.2   4505.3x
C  roots                            681.4          2.6    260.7x
C  unpropagated                     651.8          6.6     98.3x

Reproduction check against the earlier session's run of the same probe on
the same store: A 2,661.4 -> 2,735.6 (2.8%), B 14,133.5 -> 14,590.3 (3.2%),
C roots 684.0 -> 681.4 (0.4%), C unpropagated 654.0 -> 651.8 (0.3%). The
baselines reproduce. The speedup ratios move more (B 4994x -> 4505x,
C roots 234x -> 261x) because their denominators are 3-7 ms measurements
where a fraction of a millisecond is several percent -- the ratios are
order-of-magnitude claims, not three-digit ones.


--- 10,000 vertices, reps=1, B skipped -------------------------------------

$ python3 benchmarks/probe_easy.py --store /tmp/dg-bench/n10000d6 --reps 1 --skip B

store: 10,000 vertices, 11,132 edge records

fix                              now (ms)   after (ms)   speedup
A  find prose (lens cache)       47,472.4      8,351.9      5.7x
C  roots                         11,634.5         17.0    682.4x
C  unpropagated                  11,067.6         34.0    325.2x

B is skipped here because its *baseline* is the cubic term itself -- one
full ancestor walk per PROVISIONAL vertex, ~100 of them on this store, the
16.5 minutes that `results/validate-profile.txt` already measured as
`validate`. The measured `validate` timing stands in for it.


--- How the three scale from 2,500 to 10,000 -------------------------------

fix                     2,500     10,000    what happens
A  find prose            5.6x       5.7x    flat -- a constant-factor win
C  roots                 261x       682x    grows
C  unpropagated           98x       325x    grows

A is flat because the cache removes repeated lookups per vertex but each
first lookup is still a full edge scan: it divides the constant by ~5.7 and
leaves the quadratic exponent alone. C's ratios grow because the baseline is
quadratic and the fix is linear, so the gap widens with size -- which is the
signature of an exponent actually being removed, not just a constant.

Cross-check worth recording: C's fixed timings at 10,000 are the *same
numbers* the full edge index reaches. `results/index-probe.txt` has roots
11.7 s -> 17 ms (682x) and unpropagated 11.2 s -> 34 ms (333x); this probe
has 11,634.5 -> 17.0 (682x) and 11,067.6 -> 34.0 (325x). For these two
operations the four-line local fix captures the entire prize of the index,
with no invalidation story. The index's remaining advantage is elsewhere --
chiefly `find`, where A gets 5.7x and the index gets 189x.


--- The `--skip` branch --------------------------------------------------

The handoff flagged that `--skip` had never been executed. It has now, on a
200-vertex store, before the 10,000 run was trusted:

    --skip B       -> drops the B row, keeps A and both C rows
    --skip b       -> same (the flag upper-cases its arguments)
    --skip A B C   -> empty table, exits 0

It works. Two things it does that are worth knowing rather than fixing:

1. A's correctness check -- the two `selected()` calls asserting the cached
   lens picks the same rows -- runs unconditionally, outside the `if "A" not
   in skip` guard. So `--skip A` still pays one full baseline `find`. At
   10,000 vertices that is ~50 s of cost the flag does not remove. It did
   not affect the run above (A was measured anyway), but a future `--skip A`
   at scale will not be as cheap as it looks.
2. `--skip A B C` still prints "every variant asserted to return the
   identical answer" under an empty table. Only A's assertion actually ran.
